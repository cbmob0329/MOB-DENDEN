目的
街の画面を整理し、住民が暮らす箱庭に、本物の3D物理で遊べるコインプッシャーを2台追加してください。人間ユーザーが街を歩かせる操作キャラクターは削除します。住民は残します。人間ユーザーはレースへ出走できませんが、コインプッシャーは自分で操作できます。

この文書は実装仕様です。既存コードへの組み込み完了報告ではありません。対象プロジェクトは C:\Users\user\Documents\GitHub\MOB DENDEN です。今回、そのリポジトリのソース、依存ライブラリ、既存保存形式、実行結果は確認できていません。実装担当は最初に実物を確認し、既存構成に合わせてください。ファイル名や関数名を推測して既存コードの事実として扱わないでください。

納品物はこの編集用TXT、調整値のJSON案、および別添のBlender 3Dアセットです。TXT/JSONは仕様と初期案、BLEND/GLBはモデルです。ゲームの物理・財布・抽選・保存処理は実装担当が接続します。Astraその他の外部サービスへの自動送信は行いません。

1 優先順位と要件の読み方

【確定】はユーザーが求めた内容です。
【解釈案】は曖昧な部分を動く仕様にするための解釈です。
【調整案】は最初の実装・試遊に使う変更可能な数値や設計です。
【要現物確認】は既存リポジトリや端末で調べる内容です。
確定要件を変更する必要があれば、理由を示して確認してください。調整案はテスト結果と一緒に変更内容を記録します。

優先順位は、所持数と進行の保全、入力と物理の整合、ユーザーの遊びやすさ、演出、装飾の順です。見た目だけ動く試作品を完成扱いにしないでください。既存の住民、建物、ハート、レース観戦など、対象外の機能を壊さないことも受け入れ条件です。

2 参照画像と世界観

最新の参照はゲームの実行画面ではなく「コインプッシャー 3Dモデル制作ガイド」です。読み取れるデザインは次のとおりです。
・深い赤の筐体、金色の太い縁取り、星と肉球の丸い装飾
・上部に、金色で丸く柔らかい体と丸い黒サングラスのマスコット
・黒い大画面、その下に3つの報酬リール窓
・左右の斜めガラス側板、段になった押し台、実体の金色コイン
・全体は角が丸く、明るく親しみやすいカートゥーン調
・上部画面はアセット段階で空にして、実行時UIを表示できるようにする

この形と色を第一の基準にします。写実的な賭博場や他社ゲームの完全再現へ寄せないでください。2台目も同じ世界観で、縁の差し色やランプの色などで区別します。別ゲームや別ルールの台にすることは今回の確定要件ではありません。

キャラクターの対応は既知の設定に合わせます。
・モブデンデン: 黄色い顔、黒い丸サングラス、ピンクの猫耳フード
・モブピンク: 黒い顔、金色の丸眼鏡、ピンクのフード、丸い盾
小さいリール絵柄では顔とフードを優先します。参照画像にある持ち物が、自然な顔アップのトリミングで入らないことは問題ありません。キャラクター名と画像を逆にしないでください。

参照画像の実物と今回制作したモデルを確認してから接続してください。ユーザーのPCにはBlenderがないため、GLBをそのまま利用できる構成にします。BLENDは編集用の原本です。クラウド上の制作パスをユーザーのPCのパスとして扱わないでください。

3 街の操作キャラクターとレースの整理

【確定】
・街にいる住民の自律行動、見た目、名前、所持品を残す
・人間ユーザーが直接移動させる街の操作キャラクターを削除する
・人間ユーザーのレース出走を不可にする
・住民のレース参加や人間ユーザーの観戦機能は既存仕様を確認して残す
・人間ユーザーは画面の操作でコインプッシャーを遊べる

【実装指示】
操作主体を、humanUser、resident、spectator、arcadeOperatorなどの役割で区別してください。これらは新設を強制するクラス名ではなく、区別すべき意味です。既存のPlayerという名前に住民・財布・カメラ等が含まれている可能性があるため、「playerを含むものを一括削除」は禁止します。

移動入力、追従カメラ、アバター描画、レース出走権だけを適切に解除します。街の移動用ジョイスティックやアバター用ショートカットを消しても、ゲーム内の投入口ボタンは使えるようにします。住民ID、建物ID、財布の所有者IDを維持します。

保存形式を変える場合は、旧形式をバックアップしてからバージョン付きの一方向マイグレーションを行います。旧操作アバターの表示位置等が不要になっても、ハート・所持メダル・住民・進行を巻き添えで消さないでください。ユーザー識別子を削除して財布が失われる実装も不可です。

4 街のUIを整理する

【確定】UIを整理し、ゲーム画面を見やすくします。
以下のヘルプ・所持品等の具体的な整理方法は提案です。現状に大きなパネルがあることを実画面で確認した、という意味ではありません。
【調整案】
・上部の小さい帯: 戻る、ハート数、そのすぐ横に所持メダル数、メニュー
・ヘルプ、所持品、音量、演出設定は1つのメニュー内へまとめる
・説明は初回だけ短く表示し、後から「遊び方」で読み直せる
・大きな常設ログ、複数の固定パネル、同じ意味のボタンを並べない
・通知は短い一時表示にして、操作箇所や住民の顔を隠さない
・コインプッシャー中の主要操作は「左に1枚」「右に1枚」と「ハート交換」
・スマホでは親指で届く下部に投入口ボタン、上部に財布を置く
・ヘルプや所持品を開いた時はモーダルを1枚だけ表示し、閉じる操作を明確にする

タップ領域は最低44 CSS px程度を目安にし、実機で確認します。横画面必須にはせず、縦画面でも2つの投入口と盤面が読める構図を用意します。色だけで台・役・ランプ状態を伝えず、文字・輪郭・形も使ってください。これはUI提案であり、今回、既存UIのスクリーンショット監査を済ませたという意味ではありません。

5 ゲームセンターへの入場と2台の選択

【確定】
・ゲームセンターに実体のある3D筐体を2台設置する
・各筐体に2つの投入口を設ける
・入口で遊ぶかどうかを「はい／いいえ」で選べるようにする

【調整案の導線】
街でゲームセンターを選ぶ → 「ゲームセンターに入る？」 → はいで店内、いいえで街のまま。
店内では2台を同時に見せ、選んだ台にカメラを寄せる。
新規なら「遊ぶ」、保存があれば「つづきから」を表示する。
台の識別名は「1号機」「2号機」など短いものを使い、色でも区別する。
2台で共有するのは人間ユーザーの財布だけ。盤面、乱数、抽選履歴、回転待ち、景品、払い出し、押し台の位相は台ごとに保存する。
初期案では両台の確率と価値は同じにする。見た目だけで「高確率台」と誤認させない。

店内で住民が遊ぶ姿を見せます。使用中の状態と、人間ユーザーが再開できる保存の有無が分かるようにします。住民と人間ユーザーの所有権は第15節の案に従います。

6 ハートとメダルの財布

【確定】
・ハート1個をメダル10枚に交換できる
・ハートの横に所持メダル数を表示する
・ハートとメダルはゲーム内で獲得する架空の資源として扱う
・現金購入、換金、課金、広告視聴と引き換えの購入は追加しない
・景品ショップは将来用。今回の実装対象に含めない

【調整案】
左または右への1投入は所持メダル1枚を消費する。
「1ハート → 10メダル」を押すと交換内容が読める小さい確認を出し、確定時に一度だけ交換する。
ハート残高の検証、ハート-1、メダル+10、取引記録の作成を1つの原子的更新にする。
入力連打、通信再送、画面再描画があっても同じ交換IDを二度処理しない。
メダル0枚なら投入口を無効化し「メダルがありません」と交換導線を表示する。
ハート0個なら交換できない。マイナス残高、借金、自動交換は作らない。
1枚投入の残高減算と生成予約も原子的に記録する。生成できない場合は予約を保存し、未生成分を勝手に消さない。
押しっぱなしの自動連投は初期版では無効。後で追加する場合も1投入ごとの取引を維持する。

財布は整数で管理します。浮動小数の残高を使わないでください。画面の数字を先に変えて保存が失敗したまま確定扱いにしないでください。

7 通常コインの落下判定

【確定】
報酬用の穴にコインが落ちたら、その1枚を獲得すると同時にスロットを1回回す権利を得る。

【具体化】
通常コインの1個の物理IDにつき終端イベントは1回だけです。
A スロット報酬穴を通過: 所持メダル+1、回転待ち+1、物理コイン回収
B 手前の通常回収シュートを通過: 所持メダル+1、物理コイン回収
C 明示された左右のロス口を通過: 獲得なし、物理コイン回収
D 盤外異常: 保存済みの安全位置へ復帰または診断用保留。A/B/Cを勝手に起こさない

BとCの配置は実装案です。特にCを採用するなら見える形状・短いヘルプで説明します。隠れたロス判定や見えない壁で払い出しを調整しないでください。

スロット穴に入った同じコインが、その下の前面判定も通る場合でも二重加算しません。連続衝突検出や時刻順の交差判定で最初の有効な終端を確定し、状態をactiveからconsumedへ一度だけ移します。Aの「+1枚」と「+1回転」を同じ取引に含めます。

財布の増加は、実際に回収が成立した時です。投入直後、盤面に落ちた時、スロット役が出た時、見た目のキラキラが再生された時には通常コインの獲得を発生させません。

8 回転待ちと5個のランプ

【確定】
・報酬穴へ落ちた枚数分を回転権としてストックする
・表示するランプは最大5個
・実際の待ち数は5回で打ち切らず保存する
・6回待ちから1回使っても5回残るため、5個点灯したままになる

【定義】
pendingSpins: まだ開始していない回転のキュー
currentSpin: 現在処理している1回。なければnull
lampCount = min(5, pendingSpins.length)
totalUnfinished = pendingSpins.length + (currentSpinがあるなら1、なければ0)
ランプはpendingSpinsだけを表示し、現在回転中の1回は含めません。

開始時に先頭1件をpendingSpinsからcurrentSpinへ移します。終了時はcurrentSpinだけを完了にし、待ち数をもう一度減らさないでください。各キュー要素にspinId、machineId、beneficiaryId、確定結果、生成元コインIDを保存します。実装上のキュー容量を5にしないでください。長期保存の数値は安全な整数表現を使います。長いキューは永続化して必要分だけ読み込み、全件を画面やメモリへ常時展開しないでください。

テスト例
・待ち0 → 消灯
・待ち1 → 1灯 → 回転開始で待ち0、消灯
・待ち5 → 5灯 → 回転開始で待ち4、4灯
・待ち6 → 5灯 → 回転開始で待ち5、5灯 → 回転完了でも待ち5、5灯
・その次の回転開始で待ち4、4灯
・回転中に2枚入賞 → 待ちが2増え、現在回転は再開始しない
・待ち20でもデータを保持し、5灯＋小さな「待ち20」で正確な数を任意表示できる

ランプは筐体に5個置きます。スマホではランプが読みにくい場合だけ同じ情報を小さいUIに補助表示します。巨大な履歴一覧は常設しません。

10 当たり役と払い出し

以下の役は互いに排他的に1件だけ成立させます。全一致とは左・中央・右が同じ絵柄です。演出を見せた後に実際の払い出しを始めます。

【確定】
コイン袋3つ: 5枚の実体コインを盤面に降らせる。
木の宝箱3つ: 30枚の実体コインを盤面に降らせる。
金の宝箱3つ: 100枚の実体コインを盤面に降らせる。
777: 1000枚の実体コインを盤面に降らせる。非常に珍しい大当たりにする。
どら焼き3つ: 50枚の実体コインを盤面に降らせ、軽いどら焼きの立体景品を4個出す。
同じ色のMOB3つ: 画面に「M!」「O!」「B!」と順番に表示し、M/O/Bのうち1文字の立体景品を出す。
左から赤MOB、青MOB、緑MOB: M、O、Bの立体景品を3つとも出す。

どら焼きの「軽い」は物理質量をコインより低くする方向の見た目・挙動です。紙のような不安定な衝突形状にせず、押されて動く薄く丸い立体にします。

【解釈案】
・M/O/B景品は1個ごとに、手前の回収シュートへ完全に落ちた時に所持メダル+100
・どら焼き景品は4個それぞれ、手前の回収シュートへ完全に落ちた時に所持メダル+80
・どら焼き役全体では、盤面へ50枚＋景品4個×80枚の潜在価値
・景品を盤面に出した時には100/80枚をまだ加算しない
・景品の回収では財布へ一度だけ加算し、同時に100/80枚を盤面へも降らせない
・同色MOBの1文字はM/O/Bから均等選択し、抽選結果と一緒に保存する
この100/80枚の受け取り方と文字選択は解釈・調整案です。ユーザーの確定発言として扱わないでください。

【未指定を補う調整案】
モブデンデン3つ: デンデンが跳ねる短い演出の後、20枚を盤面へ降らせる。
モブピンク3つ: 盾から丸い星が広がる演出の後、40枚を盤面へ降らせる。
この2役の枚数・確率・演出は提案です。追加の隠し役や恒久ボーナスは付けません。

左から青・赤・緑など、赤→青→緑以外の5通りの色順は特別役にしません。仕様を変える場合だけ明示して追加します。MOB役と別の役を重複加算しないでください。

【景品が報酬穴へ入った場合の保護案】
通常コインと景品を型で分け、景品には報酬穴の「+1枚・+1回転」を適用しません。大きい景品が穴を塞ぎ続けないよう、通常コインの通過を妨げないガイド形状を検討します。それでも景品が穴へ落ちたら、prizeId・受取人・100/80枚の価値・未回収状態を保ったまま、安全確認済みの盤面位置へ返却する回復処理を行います。返却位置は穴から離し、再び同じ穴へ即落下する無限ループを防ぎます。空き場所がなければ返却待ちとして保存し、短い表示を出します。消滅・余分なスピン・早期の財布加算を発生させません。ガイドと返却のどちらもゲーム側で検証し、モデルだけで防止済みとしないでください。

景品は物理盤面上へ出現させます。「出現」と「手前の回収」は別イベントです。出現位置は前寄りにもできますが、初期生成だけで回収判定を横切って即獲得しない位置にします。1つの景品には一意のprizeIdとredeemed状態を持たせます。

11 抽選確率の初期案

付属JSONの重み合計を1,000,000として、各回転を1回だけ抽選します。
はずれ                 898650   89.865%
コイン袋3つ              65000    6.500%
木の宝箱3つ              20000    2.000%
金の宝箱3つ               4000    0.400%
デンデン3つ               6500    0.650%
ピンク3つ                 3500    0.350%
赤MOB3つ                   600    0.060%
青MOB3つ                   600    0.060%
緑MOB3つ                   600    0.060%
赤→青→緑MOB                100    0.010%
どら焼き3つ                 400    0.040%
777                         50    0.005%

これはユーザー指定値ではなく、試遊開始用の調整案です。777は1回あたり約1/20,000です。2万回回せば必ず出る、あるいは前回からの待ちが長ければ確率が上がる、という意味ではありません。天井や裏の確率変更は初期版に入れません。

独立した3リールの絵柄重みを何となく組み合わせず、まず排他的な役を重みで決め、その結果に一致する停止絵柄を作ります。はずれ結果の停止絵柄が偶然どれかの当たり条件にならないよう、共通の役判定関数で検証します。見せるリールと支払う役が一致することを必須にします。

穴の入賞取引でspinId、受取人、乱数位置、確定結果、設定バージョンを記録します。リールアニメーションは保存済み結果の表現です。開き直しや演出スキップで再抽選しません。確率を変更しても、すでに結果を持つ待ち回転には遡及させません。

この案の当たり率は10.135%。1回転あたり盤面へ直ちに出すコインの期待枚数は1.665枚、立体景品の額面価値の平均は0.338枚、全景品が回収されたと仮定した合計の潜在価値は2.003枚です。これは所持メダルの実際の期待増加や、投入1枚あたりの還元率ではありません。回転に至る割合、前面回収率、ロス、景品回収率、追加回転を生む連鎖に依存します。

実装後は物理を含めた長時間テストで、当たりが次の当たりを際限なく生む状態にならないか確認します。発生した報酬を後から消して調整せず、今後の新規抽選設定や穴の設計を公開されたルールの範囲で修正します。

12 演出の順序と見せ方

【確定】当たりに複数のかわいい演出を用意し、その後に実体コインを降らせます。開始、終了、イベントにも分かりやすい演出を入れます。

【調整案】
入場: 0.6秒程度でカメラが寄り、ランプが順に点灯、マスコットが小さく跳ねる。
開始: 「左か右に1枚入れよう」の短い表示。初回以外はすぐ操作できる。
回転開始: 入賞音と小さいランプの脈動。リールが約1.5秒で順番に止まる。
はずれ: 軽い終了音だけ。長い残念演出や強制待機を入れない。
通常当たり: 星、コインの輪、マスコットの拍手などから複数パターンを選ぶ。
MOB: M! → O! → B! を順に表示。立体景品出現と短い祝福。
777: 大きな777、金色の光、紙吹雪、短い専用音。その後に分割した1000枚の払い出し。
どら焼き: ふわっと跳ねるどら焼きと甘い色の光。50枚と4景品が順に現れる。
終了: 今回の投入枚数、実獲得枚数、差し引き、保存済みを短く表示する。

演出用乱数は抽選結果を変えない別系列にします。同じ役でも2〜3種類の演出から選べるようにします。点滅は過剰にせず、音量・振動・演出控えめ設定を用意します。演出スキップは見た目の時間を短くするだけで、払い出しの価値や保存状態を変えません。

1000枚の大当たりを「1000枚獲得」と即時表示しないでください。まだ盤面に出している段階では「1000枚払い出し」「残り○枚」とし、財布に入った実獲得と区別します。

13 3Dモデルとゲーム側の接続契約

別添アセットのREADMEとmanifestを最終的なノード名・寸法の参照にしてください。モデルは単なる平面画像や3D風の絵ではなく、筐体、可動押し台、コイン、景品を持つ3Dデータとして使います。

現時点の制作契約
・Blender内はメートル単位、+Zが上、-Yが正面
・Anchor_Input_L / Anchor_Input_R: (±0.255, 0.31, 1.28)
・Anchor_ChuteExit_L / Anchor_ChuteExit_R: (±0.255, 0.15, 1.041)
・Anchor_SlotCoinAndSpin: (0, -0.19, 0.80)
・Anchor_FrontFall: (0, -0.46, 0.80)
・Anchor_WinCollection: (0, -0.54, 0.44)
・Anchor_PrizeSpawn: (0, 0.05, 1.08)
・Anchor_PrizeRecovery: (0.25, -0.34, 0.88)。返却前に景品の占有範囲と空きを検証する
・可動メッシュ名: PusherPlate_MOVING
・押し台の基準移動: Y=0.17から0.055、ストローク0.115m、周期2秒
・報酬穴の開口: X=-0.085〜0.085、Y=-0.24〜-0.14
・衝突補助名: COL_Pusher、COL_SlotTrigger、COL_FrontWinTrigger
・前面操作ポッド中心: X=±0.438、Y=-0.51、Z=1.0。中央の通過幅は約0.66745m
・回収ランプ入口: (0, -0.40, 0.78)、出口: (0, -0.53, 0.69)。手前かつ下向きへ傾斜
・COL_CabinetBoundsは大まかな範囲用。盤面全体を塞ぐ巨大なsolid colliderにしない

上記はBlenderのローカル座標です。標準GLB書き出しで軸変換が行われる場合、一般にBlenderの(x,y,z)はglTFの(x,z,-y)へ移ります。ロード後の実ノード変換を検査し、数値を二重変換しないでください。エンジン上では名前でノードを解決し、そのworld transformを使う方が安全です。台を移動・回転・複製しても正しく働くことを確認します。

単体cabinet_red.glbとcabinet_blue.glbでは同じ標準ノード名を使えます。2台展示用GLBとBLENDの中では、青台側に_Blue接尾辞を付けて区別します。展示用の名前を単体モデルの名前と混同しないでください。

押し台の見た目と衝突体は1つの制御源で動かします。見た目だけアニメーションし、衝突体が止まったままでは不可です。GLBに入る形状・マテリアルと、ゲームが生成する物理体・センサー・リール表示を区別してください。

マテリアルは筐体の赤、金属金、ガラス、暗い画面、発光ランプ、コイン、各絵柄を分けます。具体的な最終マテリアル名はモデルのmanifestに合わせます。リール画像や画面表示は解像度を適切にして、文字がつぶれないようにします。

14 本物の押し出し物理とスマホ負荷

コインには厚み、質量、摩擦、反発、衝突形状を持たせます。押し台との接触によって動き、隣のコインを押し、重なり、傾き、落下できるようにします。正面へ一定速度で流すだけ、残枚数に合わせて自動回収するだけ、裏の乱数だけで落下を決める処理は不可です。

【調整案】
・物理は固定時間刻み1/60秒を基準にし、描画とは分離する
・小さいコインのすり抜けを防ぐ連続衝突検出やサブステップを必要に応じて使う
・コインは低頂点の凸形状、押し台と盤面は単純な衝突体の組合せ
・コイン同士、コインと景品、景品と押し台の接触を有効にする
・静止した物体はsleepさせ、接触で適切に起こす
・描画は共有メッシュ＋インスタンシング、影と透明ガラスは端末別に調整する
・オブジェクトプールは回収済み・ロス確定済み等の終了物体へ使う
・回転中や価値のある盤面物体を、負荷対策で黙って削除しない

最初の負荷設定案は、活動中の剛体上限450、低負荷端末は240、報酬生成最大20枚/秒です。これは保証値ではなくベンチマーク開始値です。sleep中も物体と価値は保存します。描画インスタンス化だけでは物理負荷は減らない点に注意してください。

777の1000枚を1フレームで生成しません。払い出しジョブにtotal=1000とnextOrdinalを記録し、安全に空きがある時に少数ずつ実体化します。物理上限に達したら、押し台と既存の物体を動かしながら新規生成だけ待ちます。残り枚数を保存し、消去・即時財布加算・見た目だけの粒子への置換をしないでください。上限だけを理由に当たり枚数を減らすことも不可です。

通常入力も生成容量を確認します。容量不足中は投入を一時停止し、メダルを引かないか、すでに受理した1枚は生成予約として正確に残します。払い出し中も操作を許すなら、通常投入と報酬投入が互いを永久に待たせない公平な生成順を用意します。

コインが動かず生成が進まない場合は、盤面と残価値を保持して一時停止を表示します。継続・退店保存はできるようにし、タイムアウトで景品を消さないでください。端末別LODでは装飾を先に減らし、価値や役を変えません。

目標は対応スマホで60fpsです。未計測の60fps保証はしません。低負荷設定で安定した30fpsを許容する場合は端末名と条件を報告してください。長時間発熱、メモリ、GC停止、1000枚払い出し、重なった景品で測定します。

15 住民の遊びと時間による盤面変化

【確定】
・最初の盤面にコインを配置する
・時間とともに配置が変わる
・住民もコインプッシャーで遊ぶ
・住民はそれぞれ自分のメダルを持ち、使う・得ることで増減する

【安全性を優先した実装案】
各台に「人間ユーザーの保存盤面」と「住民が使う店内盤面」の2つの文脈を持たせます。どちらもその台固有のデータです。店内で見える待機中の盤面は住民の実際の投入と押し台動作によって変化します。人間ユーザーが「つづきから」を選んだら本人の保存盤面へ切り替えます。本人が退店した盤面は停止・保存し、住民が本人の景品を勝手に持ち去らないようにします。

この盤面分離は確定要件ではなく実装提案です。将来、完全に同じ共有盤面で住民と人間ユーザーが交代する仕様にするなら、「前の人の残りコイン・景品を誰が獲得するか」「退店で何が保存されるか」をユーザーに分かるルールとして別途決めてください。無断でユーザーの進行を失わせる形では導入しません。

residentIdごとに整数のresidentMedalsを保持します。住民の投入はその住民からだけ減算し、回収・待ち回転・払い出しのbeneficiaryIdも同じ住民です。人間ユーザーのハートやメダルを住民が使ってはいけません。見た目の着席者を変えただけで未完了回転の受取人を変更しないでください。

住民AIは財布残高、遊ぶ時間、休憩を持ちます。0枚ならやめます。表示中は実際の投入イベントを生成して物理へ接続します。時間経過だけでランダムな盤面に全交換する処理は使いません。

【オフライン時間の調整案】
・本人の保存盤面と本人の財布は、閉じている間は進めない
・住民側だけ、最後に処理した時刻以降の未処理区間を一度処理する
・初期上限は30分分、1台あたり最大60投入、各住民の実際の財布の範囲内
・無制限に秒数ぶん物理ステップを一気に回さない
・住民の投入時刻、費用、抽選、獲得のイベントを作り、上限付きで段階的に再生する
・追いつき中に入場した場合も本人の盤面再開を優先し、裏の仕事は小分けにする
・同じ時間帯を再処理しない。処理済み時刻とイベントIDを保存する
・端末時計の巻き戻しは利益を発生させない。大きな時刻ジャンプは上限で丸める
・未処理分を後から何度も回収できる「残り時間の利息」にしない
・初期配置の再生成を再入場のたびに行わない

オフライン処理の結果は、住民の行動と支出に対応したものにします。人間ユーザーに無限の放置利益を与えないでください。ローカル保存だけでは意図的なデータ改変まで完全に防げないので、その意味の不正対策完了を主張しないでください。

16 状態機械とイベント処理

画面状態と、価値を持つゲーム処理状態は分離してください。
画面例: TOWN → ENTRY_CONFIRM → ARCADE_SELECT → LOADING → PLAYING → EXIT_CONFIRM → SAVING → ARCADE_SELECT
回転例: QUEUED → REEL_SPINNING → RESULT_EFFECT → PAYOUT_SCHEDULING → COMPLETE
払い出し例: QUEUED → SPAWNING → CAPACITY_WAIT → SPAWNING → COMPLETE
景品例: ON_FIELD → COLLECTED → REDEEMED
一時停止や復元はこれらを消す状態ではありません。元の状態と進捗を保存した上でPAUSED/RESTORINGとして扱います。

1 コインが報酬穴を通過する
2 coinIdが未処理か検証する
3 原子的に+1メダル、spinId作成、確定抽選、pendingへ追加、coinId消費を記録する
4 currentSpinが空で演出枠が空いた時、先頭をcurrentへ移す
5 保存済みのリール結果で回転と停止を見せる
6 結果に合う演出を1回見せる
7 同じspinIdから、払い出しジョブ/景品生成予約を一度だけ登録する
8 全予約の登録を確認してcurrentを完了にする
9 払い出しジョブは容量に応じて物理生成を継続する
10 次の回転を始める。長い払い出しがある場合は演出が重なり過ぎない速度に調整する

COMPLETEは「予約が確実に登録済み」を意味し、1000枚すべてが財布へ入ったという意味ではありません。回転・物理生成・財布獲得は別の完了状態です。

イベントの推奨情報
eventId、schemaVersion、machineId、contextId、actorId、beneficiaryId、sourceObjectId、spinId、payoutJobId、sequence、gameTick、createdAt、configVersion、payload。
実際のコードへ不要に巨大な抽象基盤を導入する必要はありませんが、所有者と一意IDを失わないでください。

17 保存と二重獲得防止

【必須】
・所持残高、取引履歴、未完了回転、確定リール結果、払い出し残数を永続保存
・台ごとの盤面、コインと景品のID/位置/姿勢/速度/状態、押し台位相を保存
・入賞、交換、投入、景品回収、払い出し登録を冪等にする
・二重タップ、再送、同じ衝突通知、再ロードで二度実行しない
・保存失敗中は新しい価値移動を止め、既存状態を保全する
・バックアップを保ち、壊れた保存を検出したら無言で初期化しない
・複数タブ/ウィンドウから同じ財布を同時に進めない。排他またはバージョン競合検出を行う

IndexedDBなど、既存環境で使えるトランザクション付きストレージを優先します。個別のlocalStorage書き込みを何回か行うだけで「原子的」と呼ばないでください。既存サーバー保存があるならその整合性方式に合わせます。

大当たりの物理生成では、payoutJobIdとordinalから生成コインIDを一意に決めます。生成済みカーソルだけ先に保存してコインを失うこと、コインだけ保存して再開時に同じordinalをもう1個作ることの両方を防ぎます。盤面スナップショットと生成カーソルを同じコミットに入れるか、永続化したイベントから再現できるようにします。

1000枚の途中で閉じた場合は、払い出し済み枚数と未払い出し枚数が合計1000であることを確認します。すでに落ちて財布へ入ったコインを盤面へ復活させてはいけません。逆に、まだ盤面にあるコインを獲得済みにして消してもいけません。

監査用の収支を持たせます。
財布残高 = 開始残高 + 交換獲得 + 通常回収 + 報酬穴回収 + 景品回収 - 投入消費
物理コインの累計生成 = 盤面中 + 通常回収済み + 報酬穴回収済み + 明示ロス済み + 診断用保留/安全返却待ち
報酬予定総数 = 生成済み数 + 未生成数
回転権の総数 = 未開始 + 現在処理中 + 完了
景品の累計生成数 = 盤面中 + 回収済み + 安全返却待ち。どの待ち状態にも一意IDと額面を保持します。
景品の額面は回収まで財布残高へ含めません。初期コインや住民盤面は文脈別に集計します。

初期配置は「初回作成済み」のフラグとseedを保存して一度だけ作ります。ユーザーが1号機と2号機を交互に開いて初期コインを無限取得できる構造にしないでください。

物理エンジンが端末間で完全決定的とは限りません。同じビルド・固定ステップの回帰テストは行いますが、異なる端末で座標が完全一致すると約束しません。重要なのは支払記録と一意IDの整合です。必要なら権威側のイベント記録を採用し、物理再現の限界を報告します。

18 戻る操作と中断からの復帰

【確定】途中離脱で状態を失わないよう、終了の確認を入れます。

戻る → 「途中の状態を保存して出ますか？」 → 「続ける」「保存して出る」。
「続ける」はモーダルだけ閉じて復帰します。
「保存して出る」は新規入力を止め、価値イベントをコミットし、物理状態と各キューを保存してから画面を移します。
スロット中・当たり演出中・1000枚払い出し中でも同じ経路で保存します。
保存が失敗したら「保存できませんでした。もう一度試す」を表示し、保存済みと偽って閉じません。

ブラウザの強制終了では確認画面が必ず出せるとは限りません。通常の価値イベント時点でこまめに保存し、visibilitychange等で追加保存します。アンロードの最後の1回だけに依存しないでください。
バックグラウンドでは本人の物理・回転演出・払い出しの進行を停止します。復帰後に経過秒数ぶん一気に物理を進めず、保存した位置から再開します。
復帰時はまず最新コミットを読み、未完了イベントを一度だけ補完します。すでに見せた演出を短縮再開してもよいですが、再抽選や再入金はしません。

退出後も未開始回転、現在回転、未生成コイン、景品があることを短い表示で分かるようにします。セーブを完了できない間は他の台への移動による財布競合も防ぎます。
